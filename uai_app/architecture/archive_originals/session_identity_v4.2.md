## 2. Design Principles

1. **Wrapper owns all ID generation.** The CLI wrapper generates the Tracking ID and (for Claude) the CLI UUID. The app reads IDs from wrapper output, never generates them.
2. **Tracking ID is the universal key.** Available from birth, human-readable, never changes, never reused. All internal references (parent-child, groups, UI state) use it.
3. **CLI UUID is a cross-reference, not a key.** It links to platform-specific data (JSONL files, conversation history). Set once, immutable after set.
4. **Terminal session name is an operational handle.** Used for attach, detach, send-keys, dump-screen. Mutable — may change on resume, may be reused across session lifetimes.
5. **Multiplexer-agnostic.** The identity model works regardless of whether tmux, zellij, or another multiplexer is the session substrate.
6. **No time-based or heuristic matching.** IDs are established by the wrapper at creation time and linked deterministically. UUID discovery uses a breadcrumb file written by the wrapper — never timestamp proximity, never fuzzy matching.
7. **Atomic writes.** All registry and sessionInfo writes use temp-file + rename. Readers never see partial JSON.
8. **Reconciliation.** Missing or inconsistent state is recoverable — see Section 11.

### 3.2 Tracking ID Format

```
{platform}_{YYYYMMDD}_{HHMMSS}[_{NNN}]
```

- **platform**: `claude`, `codex`, `gemini` (short form — the `_cli` suffix used in sessionInfo's `platform` field (`claude_cli`, `codex_cli`, `gemini_cli`) is the full form. The Tracking ID uses the short form for brevity.)
- **YYYYMMDD_HHMMSS**: **UTC** time of session creation
- **_NNN**: Three-digit rolling index (`_002`, `_003`, ..., `_999`), only appended on same-platform+same-second collision

Examples:
```
claude_20260330_061500
codex_20260330_061512
gemini_20260330_061512_002   <- second gemini session in the same second
```

**Properties:**
- Human-readable — platform and creation time visible at a glance
- Self-sorting — lexicographic order matches chronological order within platform (UTC avoids DST/timezone ambiguity)
- Globally unique — same-second collisions handled by rolling index
- Immutable — never changes after creation
- Consistent with `created_at` — both use UTC, year partition is unambiguous

**Collision handling — atomic allocation:** The wrapper allocates the Tracking ID atomically using `mkdir` (which is atomic on POSIX). The wrapper attempts `mkdir session_registry/{platform}/{yyyy}/{tracking_id}.d`. If it succeeds, the ID is claimed. If it fails (directory exists), the wrapper increments the rolling index and retries. The `.d` directory is replaced with the actual `.json` file after sessionInfo is written. This prevents race conditions when multiple wrappers launch concurrently (e.g., spawning a wave of workers).

**Overflow:** Rolling index supports `_002` through `_999` (998 collisions per platform per second). Exceeding this is operationally impossible and treated as an error.

### 3.3 CLI UUID

The platform's own conversation/session identifier.

├──────────┼──────────────────────────────────────┼────────────────────────┼──────────────────────────────────────────┤

├──────────┼──────────────────────────────────────┼────────────────────────┼──────────────────────────────────────────┤

**For Claude:** The wrapper generates the UUID, passes it to the binary via `--session-id`, and writes it to the registry immediately. The uuid8 (first 8 hex chars) is embedded in the terminal session name for visual correlation.

**For Codex/Gemini:** The wrapper writes the registry entry with `cli_uuid: null`. A filesystem watcher (`ensure_session_watcher.sh` + `handle_new_session_file.py`) detects the new session file and updates the registry with the discovered UUID.

### 3.4 Terminal Session Name

The multiplexer session name used for terminal operations.

**For zellij:** `{display_name}_{uuid8}` (e.g., `mvcr2_visual_design_f7ec75a4`)
**For tmux:** Similar convention, TBD per multiplexer abstraction.

The terminal session name is:
- Created by the wrapper at launch
- Mutable — a session may be resumed into a different terminal session name
- Not guaranteed unique across session lifetimes — a name may be reused after a session is cleaned up
- Never used as a key or stable reference in the app or registry

### 3.5 Correlated UUID (Claude only)

For Claude sessions, the CLI UUID and terminal session name share a visual correlation:

```
Terminal:  my_chat_7d685436
CLI UUID:  7d685436-7f00-43d0-a14f-d53159eeaaa5
           ^^^^^^^^
           same 8 chars
```

This is a convenience for human debugging, not a system invariant.

## 4. Data Stores

### 4.1 Per-Session Directory (Source of Truth)

**Location:** `ai_general/data/sessions/{platform}/{yyyy}/{tracking_id}/`
**Writers:** CLI wrappers (at creation, resume, fork), fswatch handler (UUID discovery)
**Readers:** App, scripts, MCP servers, other wrappers

**Structure:**
```
sessionInfo.json          # Identity + metadata (source of truth)
chat_history.jsonl ->     # Symlink to JSONL file (once cli_uuid known)
chat_history/             # Directory of JSONL symlinks (across project dir changes)
pids/                     # PID history (zero-sized files, all preserved)
  {pid}.{yyyymmdd_HHMMSS}
```

**sessionInfo.json:**
```json
{
  "schema_version": 2,
  "tracking_id": "claude_20260330_061500",
  "cli_uuid": "7d685436-7f00-43d0-a14f-d53159eeaaa5",
  "platform": "claude_cli",
  "terminal_session": "my_chat_7d685436",
  "parent_tracking_id": "claude_20260330_060000",
  "parent_cli_uuid": "a9563ba0-421c-4df9-b4de-...",
  "created_at": "2026-03-30T06:15:00Z",
  "display_name": "my_chat",
  "working_dir": "$HOME/Documents/AI/ai_root",
  "model": "opus",
  "roles": ["chat"]
}
```

| Field | Type | Mutable? | Description |
|-------|------|----------|-------------|
| `schema_version` | int | No | Schema version (2 for v4) |
| `tracking_id` | string | No | App primary key |
| `cli_uuid` | string? | Write-once | Platform conversation UUID. Null until discovered (Codex/Gemini). |
| `platform` | string | No | `claude_cli`, `codex_cli`, `gemini_cli` |
| `terminal_session` | string? | Yes | Current terminal session name. Null for --no-mux/--oneshot sessions. Updated on resume. |
| `parent_tracking_id` | string? | No | Parent's tracking ID. Null for top-level. |
| `parent_cli_uuid` | string? | No | Parent's CLI UUID. Null for top-level. |
| `created_at` | string | No | ISO timestamp |
| `display_name` | string | Yes | Human-readable name |
| `working_dir` | string? | No | Project directory at launch |
| `model` | string? | No | Model override if specified |
| `roles` | string[] | Yes | Agent roles |

### 4.2 Session Registry (Derived Index)

**Location:** `ai_general/data/session_registry/{platform}/{yyyy}/{tracking_id}.json`
**Writers:** CLI wrappers, fswatch handler
**Readers:** App, scripts

The registry is a **derived index** — it contains the identity subset of sessionInfo and is fully rebuildable from session info dirs.

**Contents:** Same identity fields as sessionInfo (tracking_id, cli_uuid, platform, parent_tracking_id, parent_cli_uuid, created_at).

**Reverse-lookup symlinks:**
```
session_registry/claude_cli/2026/
  claude_20260330_021500.json                     # actual file
  7d685436-7f00-43d0-a14f-d53159eeaaa5.json ->   # symlink (CLI UUID lookup)
    claude_20260330_021500.json
```

**Lookup paths:**
- By Tracking ID: `session_registry/{platform}/{yyyy}/{tracking_id}.json` -> O(1)
- By CLI UUID: `session_registry/{platform}/{yyyy}/{uuid}.json` (symlink) -> O(1)
- By terminal session name: Scan registry files for matching `terminal_session` field (linear, used only for legacy/discovery)

### 4.3 App-Specific Data

**Location:** `ai_general/data/unified_cli/` (app owns this entirely)
**Writers:** App only
**Readers:** App only

**Global app state** (`app_state.json`): tabs, active tab, groups, UI preferences.
**Per-session app data** (`sessions/{tracking_id}.json`): type, pinned, prompt history, exchange count.

Session type (chat/worker), pinned state, and all UI-only state lives here. The app merges this with registry + sessionInfo at load time.

## 5. Parent-Child Detection

Automatic — no explicit params needed.

The wrapper detects the parent by reading the `TERMINAL_SESSION_NAME` environment variable (set natively by tmux/zellij in every session). Before creating a new session, the wrapper:

1. Reads the current terminal session name from the environment
2. Looks up the corresponding Tracking ID in the registry
3. Records it as `parent_tracking_id`

For top-level sessions (bare terminal, app launcher, cron): the env var is either not set or doesn't match any registry entry.

The env var name depends on the multiplexer:
- Zellij: `ZELLIJ_SESSION_NAME`
- tmux: `TMUX` (parsed) or a wrapper-set var

The session substrate abstraction provides `get_current_session_name()` to normalize this.

## 6. CLI UUID Discovery

**The wrapper discovers the CLI UUID before exiting.** No external watchers, no breadcrumbs, no async discovery pipeline.

| Platform | Method | Timing |
|----------|--------|--------|
| Claude | Wrapper generates UUID v4, passes to binary via `--session-id` | Immediate (before launch) |
| Codex | Wrapper polls `~/.codex/sessions/` for new file after launch | Seconds after launch (wrapper waits) |
| Gemini | Wrapper polls `~/.gemini/tmp/<project>/chats/` for new file after launch | Seconds after launch (wrapper waits) |

### Discovery flow (Codex/Gemini)

```
1. Wrapper snapshots the session file directory (list existing files)
2. Wrapper creates terminal session + launches CLI binary
3. Wrapper polls for a new file not in the snapshot (timeout: 30s)
4. New file appears → extract UUID:
   - Codex: filename pattern rollout-DATE-<uuid>.jsonl
     UUID is the last 36-char segment matching [0-9a-f-]{36}
   - Gemini: read sessionId field from the JSON file
5. Write cli_uuid to sessionInfo.json and registry
6. Create CLI UUID reverse-lookup symlink
7. Print TRACKING_ID, TERMINAL_SESSION, CLI_UUID to stdout
8. Exit
```

**Why this works:** The wrapper fork+execs the multiplexer command (`zellij` or `tmux`) via `Popen`. The wrapper does NOT exit immediately — it waits for the session file to appear. The CLI binary starts inside the multiplexer session and creates its session file within seconds. The wrapper detects the new file by diffing against its pre-launch snapshot.

**No time-based matching.** The snapshot diff is deterministic: files present before launch are excluded, any new file is from this launch. Concurrent wrapper launches are safe because each wrapper takes its own snapshot before its own launch.

**Timeout:** If no new file appears within 30 seconds, the wrapper writes `cli_uuid: null` and prints `CLI_UUID=pending`. This is a fallback for cases where the CLI binary fails to start or creates its file in an unexpected location. The `resolve_missing_uuids.py` script can be run manually to fill gaps.

**No external infrastructure required.** No fswatch, no breadcrumbs, no handler scripts, no cron cleanup. The wrapper owns the entire identity lifecycle.

## 7. Identity Block

Injected by the wrapper into both system prompt and first user prompt:

```
<<<SESSION_IDENTITY>>>
Tracking ID: claude_20260330_061500
CLI session ID: 7d685436-7f00-43d0-a14f-d53159eeaaa5
Terminal session: my_chat_7d685436
Parent: claude_20260330_060000
<<<END SESSION_IDENTITY>>>
```

Since the wrapper waits for UUID discovery before launching the bootstrap prompt, the CLI UUID is available in the identity block for all platforms. In the rare timeout case (`cli_uuid: null`), the `CLI session ID` line is omitted.

The markers prevent false matches when content is pasted between sessions.

## 8. CLI Wrapper Interface

### 8.1 Parameters

```
Positional:
  [prompt]                 Initial prompt text. Omit for bare interactive session.

Session Identity:
  -n, --name NAME          Display name (used in terminal session name generation)
  --session-id UUID        Explicit CLI UUID (Claude only; auto-generated if omitted)

Session Lifecycle:
  -r, --resume ID          Resume session by Tracking ID or CLI UUID
  -f, --fork-from ID       Fork from parent session (Tracking ID or CLI UUID)

Execution:
  -t, --targetDir DIR      Working/project directory
  -A, --agent ROLE[,ROLE]  Agent roles (comma-separated)
  -m, --model MODEL        Model override
  --oneshot                Non-interactive: run prompt, print output, exit
  --dry-run                Print bootstrap prompt without invoking binary
  --start-clean            Skip all bootstrap
  --no-mux                 Run without multiplexer (direct foreground)
  -a, --auto-approve       Skip permission prompts (default: enabled)
  --no-auto-approve        Require permission prompts
  -T, --task FILE          Load task instructions from file
  --any-task               Claim first available task from queue
  --pre-prompt TEXT        Prepend to bootstrap prompt
  --post-prompt TEXT       Append to bootstrap prompt
  -o, --output FILE        Write output to file
```

### 8.2 Wrapper Output

On successful launch, the wrapper prints to stdout:

```
TRACKING_ID=claude_20260330_061500
TERMINAL_SESSION=my_chat_7d685436
CLI_UUID=7d685436-7f00-43d0-a14f-d53159eeaaa5
```

The wrapper waits for UUID discovery before printing output, so `CLI_UUID` is normally populated for all platforms. In the rare timeout case (CLI binary failed to create a session file within 30s):
```
TRACKING_ID=codex_20260330_061512
TERMINAL_SESSION=codex_dev_lead_a3f7b2c1
CLI_UUID=pending
```

`CLI_UUID=pending` means the binary launched but didn't create a session file in time. The session functions via Tracking ID; transcript is unavailable until UUID is resolved manually.

### 8.3 Wrapper Logic (New Session)

```
1.  PLATFORM = "claude_cli" (or codex_cli, gemini_cli)
2.  TRACKING_ID = generate_tracking_id(PLATFORM) — atomic allocation
3.  SET PARENT IDs (from env: current terminal session -> registry lookup)
4.  SET CLI UUID:
    - Claude: from --session-id or generate UUID v4
    - Codex/Gemini: snapshot session file directory (for post-launch discovery)
5.  UUID8 = CLI_UUID[0:8] (Claude) or random hex (Codex/Gemini)
6.  SET TERMINAL SESSION NAME (from -n/--name + UUID8, or auto-generated)
7.  SET DIRS (from -t/--targetDir or derive)
8.  ROLES = from -A/--agent or ["chat"]
9.  Write registry file + per-session dir + sessionInfo.json + PID file
    - Claude: cli_uuid written immediately
    - Codex/Gemini: cli_uuid written as null (updated in step 12)
10. Create terminal session (via session substrate abstraction)
    - Substrate returns actual session name (may differ from requested)
    - Update terminal_session in sessionInfo if name changed
11. Launch CLI binary inside terminal session
12. DISCOVER CLI UUID (Codex/Gemini only):
    - Poll for new file in session file directory (vs pre-launch snapshot)
    - Extract UUID from filename (Codex) or file content (Gemini)
    - Update sessionInfo.json and registry with cli_uuid
    - Create CLI UUID reverse-lookup symlink
    - Timeout 30s: leave cli_uuid as null, print CLI_UUID=pending
13. Print TRACKING_ID, TERMINAL_SESSION, CLI_UUID to stdout
14. Exit
```

### 8.4 Wrapper Logic (Resume)

```
1.  SESSION_INFO = lookup(resume_id)  -- by Tracking ID or CLI UUID
2.  If not found: ERROR
3.  Error if combined with --session-id or --model
4.  Check terminal session status. If running: ERROR (already active)
5.  SET DIRS (from -t/--targetDir or SESSION_INFO.working_dir)
6.  Update sessionInfo: terminal_session (may change), PID file
7.  Attach to or create terminal session
8.  Inside session: resume CLI binary with CLI UUID
```

### 8.5 Wrapper Logic (Fork)

```
1.  PARENT_INFO = lookup(fork_from_id)
2.  If not found or no cli_uuid: ERROR
3.  SET PARENT IDs from PARENT_INFO
4.  Generate new TRACKING_ID + CLI UUID + TERMINAL SESSION NAME
5.  Check collision: new TRACKING_ID must not exist. Error if it does.
6.  Write registry + session dir (with parent fields)
7.  Create terminal session
8.  Launch CLI binary with --resume PARENT_CLI_UUID --fork-session --session-id NEW_CLI_UUID
```

## 9. Session Substrate Abstraction

The identity model is independent of the terminal multiplexer. A session substrate interface provides:

```python
class SessionSubstrate(ABC):
    """Abstract interface for terminal multiplexer operations."""

    @abstractmethod
    def create_session(self, name: str, command: list[str], cwd: str, log_file: Path | None = None) -> str:
        """Create a new named session running the given command. Returns actual session name used."""

    @abstractmethod
    def session_exists(self, name: str) -> bool:
        """Check if a session with this name exists (running or stopped)."""

    @abstractmethod
    def session_is_running(self, name: str) -> bool:
        """Check if a session is actively running (not exited/stopped)."""

    @abstractmethod
    def kill_session(self, name: str) -> None:
        """Terminate a session."""

    @abstractmethod
    def list_sessions(self) -> list[SessionInfo]:
        """List all sessions with name, status, creation time."""

    @abstractmethod
    def send_keys(self, name: str, keys: str) -> None:
        """Send keystrokes to a session."""

    @abstractmethod
    def dump_screen(self, name: str, path: Path | None = None) -> str:
        """Capture current screen content."""

    @abstractmethod
    def get_current_session_name(self) -> str | None:
        """Get the terminal session name of the environment we're running in."""

    @abstractmethod
    def attach(self, name: str) -> None:
        """Attach to a session (for interactive use)."""
```

Implementations: `ZellijSubstrate`, `TmuxSubstrate`, `NoneSubstrate` (for `--no-mux`/`--oneshot`).

`NoneSubstrate` runs the command in the foreground with no multiplexer. `terminal_session` is null. Only `send_keys` is supported (via stdin pipe). `attach`, `dump_screen`, and `list_sessions` raise errors.

The active substrate implementation is a system-level configuration, not a per-session attribute. All sessions on a given machine use the same multiplexer. The app and MCP servers call the abstraction interface — they never know or care which concrete implementation is behind it.

**Name returned from create:** `create_session` returns the actual session name used (which may differ from the requested name if the substrate normalizes it). The wrapper uses this return value, not the requested name.

## 10. Session Lifecycle

| Event | Tracking ID | CLI UUID | Terminal Session | Registry | Session Dir |
|-------|-------------|----------|-----------------|----------|-------------|
| **New** | Generated | All platforms: set by wrapper before exit (null on timeout) | Generated | Created (complete) | Created (complete) |
| **Resume** | Unchanged | Unchanged | May change (new terminal session) | Updated (terminal_session) | Updated (PID file) |
| **Fork** | NEW | NEW | NEW | NEW file (parent fields set) | NEW dir |
| **Stop** | Unchanged | Unchanged | Unchanged | Unchanged | PID file preserved |
| **Rename** | Unchanged | Unchanged | Unchanged | Unchanged | display_name updated |
| **Finalize** | Unchanged | Unchanged | Unchanged | Unchanged | Wrap-up content produced, session archived |

## 11. Reconciliation

| State | Action |
|-------|--------|
| Registry exists, session dir missing | Warn. Rebuild session dir from registry fields if possible. |
| Session dir exists, registry missing | Rebuild registry file from sessionInfo.json. |
| CLI UUID symlink missing | Scan for matching `cli_uuid` field, recreate symlink. |
| Both missing | Session unknown. Discovery script may find it from platform session files. |
| `cli_uuid` is null, session stopped | Mark as unresolved. `resolve_missing_uuids.py` can attempt PID/breadcrumb matching or flag for manual resolution. |
| Terminal session name in registry doesn't match any live session | Normal (session stopped). No action needed. |
| Same terminal session name exists in both tmux and zellij | Not possible — system uses one multiplexer at a time (system-level config). |

## 12. Edge Cases

| Case | Handling |
|------|----------|
| CLI binary doesn't create session file within 30s | Wrapper writes `cli_uuid: null`, prints `CLI_UUID=pending`. Session functions via Tracking ID. Transcript unavailable. `resolve_missing_uuids.py` can fill gaps manually. |
| Multiple wrappers launch concurrently | Each takes its own snapshot before launch. Snapshot diffs are independent — no cross-contamination. Tracking ID allocation is atomic (mkdir). |
| `--no-mux` / `--oneshot` sessions | `terminal_session: null`. No terminal operations (dump_screen, attach). JSONL file is the only data source. App shows session in navigator but cannot attach terminal. |
| `cli_uuid` never resolves | Stays null permanently. Session functions without it — Tracking ID is the primary key. Transcript unavailable (no JSONL to link). |
| Terminal session renamed outside the wrapper | Wrapper's `terminal_session` field becomes stale. App detects via polling (live session name not in registry). `terminal_session` updated on next resume. |
| Launch failure (terminal session creation fails) | Wrapper writes registry + sessionInfo before creating session (step 9). If step 10 fails, the registry entry exists with no live session. Reconciliation detects this (registry exists, no live session, no PID) and marks as failed. Wrapper returns non-zero exit code. |
| Concurrent writes to sessionInfo by wrapper + app | Atomic writes (temp-file + rename). Wrapper writes identity fields; app writes UI fields to separate app-data files. sessionInfo.json is only written by wrappers. |
| Malformed sessionInfo.json | Reader logs error, treats session as if sessionInfo is missing. Reconciliation rebuilds from registry + platform files. |
| v3 migration: multiple sessions with same-second creation | Rolling index applied during migration (`_002`, `_003`, etc.). |

## 13. Migration from v3

- **v3 registry entries** (keyed by zellij name) can be migrated by generating Tracking IDs from `created_at` + `platform` fields
- **v3 sessionInfo.json** directories renamed from `{zellij_name}/` to `{tracking_id}/`
- **Discovery script** can rebuild the v4 registry from v3 session dirs + live session data
- **Old zellij names** preserved as `terminal_session` field values
- **No migration script required for v3 -> v4** — the discovery script rebuilds everything

1. **Gemini UUID format:** Gemini uses a short UUID (8 hex chars) in filenames. Is the `sessionId` field inside the JSON a full UUID or also short? Needs verification against live session files.

2. **Terminal session name format for tmux:** The zellij convention is `{display}_{uuid8}`. Should tmux use the same, or does tmux have naming constraints that require a different format?

3. **`working_dir` mutability:** Currently marked immutable (set at creation). But sessions can be resumed into a different directory via `-t/--targetDir`. Should `working_dir` track the initial launch directory (immutable) or the current project directory (mutable, updated on resume)? If immutable, the app may need a separate runtime `current_dir` field.
