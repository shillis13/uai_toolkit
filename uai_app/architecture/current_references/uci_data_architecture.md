# UCI App Data Architecture

**Author:** Pixel (UX Designer)
**Date:** 2026-04-18
**Revised:** 2026-04-19 (review feedback from Gemini + Codex + PianoMan, corrections from walkthrough)
**Status:** Approved — ready for implementation

## 1. Principles

1. **Each piece of data has exactly one source of truth (SSOT).** No field is authoritative in two places.
2. **Data that exists beyond the app goes in SQLite.** Scripts, CLI wrappers, and other tools depend on it.
3. **Data that only the app cares about goes in app files.** `folders.json` for containment, `app_state.json` for UI preferences.
4. **Ephemeral/derived data lives in memory only.** If it can be reproduced from authoritative sources, don't persist it.
5. **Containers own their children.** Folders know their subfolders and cards. No reverse-pointer-only structures.
6. **Actions are typed commands.** The renderer never directly mutates domain data. It dispatches commands to the main process, which returns updated state.

## 2. Card Identity

Sessions and Briefs are both "cards" that live in folders. To avoid identity collisions, all card IDs are globally namespaced:

```
session:<tracking_id>     e.g., session:20260413_200951_d2e3b973_cla
brief:<brief_name>        e.g., brief:pixel_ux_uci_app
```

All generic card APIs (folders, tags, navigation) use namespaced `CardId`. Session-specific APIs accept raw `sessionId` when explicitly named. Brief-specific APIs accept raw `briefName` when explicitly named.

```typescript
type CardId = string;  // must be "session:<id>" or "brief:<id>"
```

## 3. Conceptual Model

Five distinct concepts. They do not overlap:

| Concept | What it answers | Storage |
|---|---|---|
| **Folders** | Where did I put this? | `folders.json` |
| **Views** | Show me a filtered subset | Computed at runtime (not stored) |
| **Tags** | What metadata label does this have? | SQLite |
| **Groups** | What relationship does this session have? | SQLite |
| **Briefs** | What condensed knowledge artifact exists? | YAML on disk (content) + SQLite (registry) |

Views are computed filter presets over session metadata. They are NOT Groups, NOT Folders, NOT stored entities. Platform views (Claude/Codex/Gemini), Archive view, and Condenser view are all computed from session properties and tags.

## 4. Data Classification

### 4.1 Beyond-App Data (SQLite — `session_store.py`)

Data that has meaning outside the UCI Electron app.

#### Sessions

| Field | Description |
|---|---|
| id / tracking_id | Primary identity |
| terminal_session | Terminal/substrate session name |
| cli_session_id | CLI platform UUID |
| platform | claude_cli, codex_cli, gemini_cli |
| created_at | Creation timestamp |
| display_name | Human-readable name |
| role | Agent role (chat is implied when role = assistant) |
| working_dir | Working directory at launch |
| project_dir | Project root |
| transcript_path | Path(s) to JSONL history file(s) |
| archived | Boolean — user explicitly archived this session |

#### Tags

Normalized table:

```sql
card_tags (
  card_id TEXT NOT NULL,   -- namespaced: "session:..." or "brief:..."
  tag TEXT NOT NULL,
  PRIMARY KEY(card_id, tag)
)
```

Currently only one tag: `condenser`. Data model supports future expansion. No UI to create arbitrary tags.

#### Entity Relationships

A single generic edge table for all relationships between sessions, briefs, and other entities:

```sql
entity_relationships (
  source_type TEXT NOT NULL,    -- 'session' | 'brief'
  source_id TEXT NOT NULL,
  relation_type TEXT NOT NULL,  -- 'forked_to' | 'launched' | 'brief_of' | 'loaded_by' | 'supersedes' | 'relates_to'
  target_type TEXT NOT NULL,    -- 'session' | 'brief'
  target_id TEXT NOT NULL,
  created_at TEXT,
  metadata_json TEXT,
  PRIMARY KEY(source_type, source_id, relation_type, target_type, target_id)
)
```

Paired relationships (e.g., `forked_from`/`forked_to`) are stored as a single row; the inverse is derived by query.

`parent_tracking_id` remains as a legacy/convenience column on the sessions table, but the relationships table is authoritative for graph traversal.

#### Brief Metadata

| Field | Description |
|---|---|
| name | Unique identifier (filename stem) |
| display_name | Human-readable |
| description | Auto-generated by Condenser |
| status | active, superseded, archived |
| created_at | Creation timestamp |
| updated_at | Last modification timestamp |
| condenser_session | Which session did the condensation |
| brief_path | Path to YAML content file |
| schema_version | Brief YAML format version |
| content_hash | SHA256 of YAML content for change detection |
| archived_at | Timestamp if archived |

The Brief YAML file on disk remains the content store. SQLite holds the registry for queryability.

Brief relationships (brief_of, loaded_by, supersedes) use the `entity_relationships` table above.

#### Groups

```sql
groups (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  type TEXT NOT NULL,        -- 'project_team' | 'functional_team' | 'custom'
  description TEXT,
  created_at TEXT,
  updated_at TEXT,
  archived BOOLEAN DEFAULT 0
)

group_members (
  group_id TEXT NOT NULL,
  session_id TEXT NOT NULL,
  role_in_group TEXT,
  added_at TEXT,
  PRIMARY KEY(group_id, session_id)
)
```

Groups represent domain relationships — team composition, functional grouping, project affiliation. They affect communications, interactions, and responsibility scope.

Groups are separate from Folders. A session can be in one Folder (containment) AND multiple Groups (relationships). Groups are always explicit/manual — no computed membership.

### 4.2 App-Only Organization (folders.json)

Data that only the UCI app uses for organizing the user's workspace.

```typescript
type CardId = string;  // "session:<id>" or "brief:<id>"

interface Folder {
  id: string;
  name: string;         // unique within same parent
  icon?: string;
  color?: string;
  builtin: boolean;
  subfolders: string[]; // ordered IDs of child folders
  cards: CardId[];      // ordered namespaced card IDs
}

interface FolderStore {
  schema_version: number;
  revision: number;           // incremented on every write
  roots: {
    sessions: string;         // "all_sessions"
    briefs: string;           // "all_briefs"
  };
  folders: Record<string, Folder>;
}
```

**Rules:**
- Containers own children — `subfolders[]` and `cards[]` on each folder
- A card belongs to exactly one folder (or root if unassigned)
- "Move to Folder" removes from old folder's `cards[]`, adds to new folder's `cards[]`
- Folder names unique within same parent
- Two roots: `all_sessions` (session folder tree), `all_briefs` (brief folder tree)
- Session cards may only appear under the sessions root tree
- Brief cards may only appear under the briefs root tree
- No card appears in two folders
- No View folders — platform/status views are computed filters, not folders
- Root folders cannot be moved or deleted

**Validation rules** (enforced after every mutation, always in dev builds):
- Every folder is reachable from exactly one root
- No cycles in the tree
- No folder appears in two parents' `subfolders[]`
- No card appears in two folders' `cards[]`
- `cards[]` entries are valid namespaced CardIds
- Builtin folders cannot be deleted

### 4.3 App UI State (app_state.json)

User preferences and workspace layout. Pure UI — no domain meaning.

```json
{
  "schema_version": 2,
  "tabs": {
    "openTabs": ["session_1", "session_2"],
    "activeTabId": "session_1",
    "viewHistory": {
      "backStack": ["session_1", "session_2"],
      "forwardStack": []
    }
  },
  "sessions": {
    "session_1": {
      "pinned": true,
      "promptbox": {
        "stage_prompt": true,
        "rewrite": { "enabled": false },
        "reminders": []
      }
    }
  },
  "folder_prefs": {
    "folder_abc": {
      "collapsed": true,
      "show_all_descendants": false
    }
  }
}
```

| Field | Scope | Description |
|---|---|---|
| tabs.openTabs | Global | Ordered list of open tab session IDs |
| tabs.activeTabId | Global | Currently focused tab |
| tabs.viewHistory | Global | Back/forward stack of tab IDs for tab switching history |
| pinned | Per-session | Session is pinned in UI. UCI-only — no domain meaning outside the app. |
| folder_prefs.collapsed | Per-folder | Folder is collapsed in navigator |
| folder_prefs.show_all_descendants | Per-folder | Show recursive children in CardListView |
| promptbox_config | Per-session | Stage prompt Y/N, re-write config, reminders |

### 4.4 Renderer Memory (Not Persisted)

Derived or ephemeral data. Lives only during the app's lifetime.

| Data | Source | Notes |
|---|---|---|
| Terminal/substrate state (connected/disconnected/killed) | Substrate query on startup + polling | Everything starts as "unknown"; substrate provides truth |
| Interaction/runtime state (running/idle/stopped) | Terminal output observation | Independent from terminal state |
| Exchange count | Derived from JSONL | Cached metric, recomputable. If cached, invalidated by transcript mtime/hash — never SSOT. |
| Prompt history (up/down arrow) | Derived from JSONL | Recomputable |
| Session kind (chat/worker) | Derived from role | Has assistant/chat role = chat, else worker. If role missing on legacy sessions, kind = "unknown". |
| Search criteria and results | User input | Ephemeral, persists during app lifetime |
| Filter criteria (per-view) | User input | Ephemeral |
| Transcript filter state | User input | Ephemeral |
| Breadcrumb path | Derived from folder tree | Computed, not stored |
| Reverse indexes (card to folder, folder to parent) | Derived from folders.json | In-memory lookup optimization |
| Current folder browser location | Renderer state | Which folder the center pane is showing |
| Statusline telemetry (context %, rate limits, model, tokens) | Claude Code statusline-command.sh | Read current values from each status update, discard. Not persisted. |

## 5. Data Flow

### 5.1 Persistent Write Paths

| Store | Writers | Write mechanism |
|---|---|---|
| SQLite | CLI wrappers / launcher / session capture | `session_store.py` API for create AND update of session identity, UUID, transcript path, lineage, lifecycle fields. Not launch-only — fields are updated post-launch (UUID discovery, rename, archive, relationship establishment). |
| SQLite | App main process | `session_store.py` subprocess calls for tags, archive, display name, relationships, group membership |
| SQLite | `condense.py` | Brief metadata + relationships during condensation |
| SQLite | External scripts | Any tool using `session_store.py` API |
| Brief YAML | `condense.py` / app main process via `briefs.create` | Atomic file write, then SQLite metadata update with brief_path + content_hash |
| folders.json | App main process ONLY | `updateFolderStore(mutator)` — atomic read-modify-write |
| app_state.json | App main process ONLY | `updateAppState(mutator)` — atomic read-modify-write |

**Key constraints:**
- `folders.json` and `app_state.json` have exactly one writer (app main process). No external tool writes to these.
- SQLite has multiple writers coordinated through `session_store.py`.
- Brief YAML changes must go through the brief/session_store API, which updates `content_hash` and emits the SQLite change signal. Raw YAML edits are not automatically tracked.
- Groups: app main process writes via `session_store.py`. External scripts may also create/modify groups through the same API. (Groups are future — initial implementation may be app-only.)

**SQLite signal contract:** All SQLite writers MUST use `session_store.py`. `session_store.py` MUST touch/write the `sessions.changed` signal file after every successful commit. Raw SQLite writes that bypass this contract are unsupported.

### 5.2 Ephemeral Runtime Inputs

These data sources are NOT persisted stores. They feed renderer memory only.

| Source | How main process receives it | What it provides |
|---|---|---|
| Terminal/substrate state changes | Substrate poll/watch, attach/detach callbacks | connected, disconnected, killed per session |
| Interaction/runtime state changes | Terminal output observer, prompt detection, process state | running, idle, stopped per session |
| Statusline telemetry | Parsed from Claude Code statusline-command.sh callback | context %, rate limits, model, tokens. Throttled/coalesced — high frequency source. |
| Transcript-derived metrics | Recomputed on demand when opening session detail | Exchange count, prompt history. Non-authoritative cache. |
| Renderer navigation state | Renderer only, commanded via main bridge | Current folder browser location, card detail view, filter view |

### 5.3 Change Notification — Two Channels

Data changes flow through two separate notification channels to the renderer:

**Channel 1: `onStoreChanged`** — durable/persisted store changes

```
Persistent data change (SQLite, folders.json, app_state.json, Brief YAML)
  → Main process detects change
  → Main process emits: onStoreChanged(event)
  → Renderer refreshes ONLY the affected store(s)
```

**Channel 2: `onRuntimeChanged`** — ephemeral state changes

```
Runtime state change (terminal state, interaction state, statusline)
  → Main process detects change
  → Main process emits: onRuntimeChanged(event)
  → Renderer updates runtime/telemetry state only — never triggers store refresh
```

Statusline updates are high-frequency. They flow through `onRuntimeChanged` and are throttled/coalesced. They never trigger session/folder/appState refresh.

#### Change detection by source:

| Source | How main process detects it |
|---|---|
| App's own commands | Command handler knows what it changed — emits immediately after write |
| External SQLite writes | `sessions.changed` signal file + `fs.watch` with debounce. Fallback: periodic mtime/revision poll every N seconds. |
| Terminal/substrate state | Substrate poll/watch, attach/detach callbacks |
| Interaction/runtime state | Terminal output observer |
| Statusline telemetry | Statusline callback, throttled |
| Brief YAML content | Not auto-detected. Brief API updates SQLite + signal. Manual refresh/repair for raw edits. |

#### Store change event:

```typescript
window.terminalApi.onStoreChanged(callback: (event: StoreChangedEvent) => void)

interface StoreChangedEvent {
  eventId: string;                        // unique event ID
  sequence: number;                       // monotonic sequence number
  commandId?: string;                     // if triggered by a command, its ID
  changed: Array<'sessions' | 'folders' | 'appState' | 'briefs' | 'groups'>;
  source: 'command' | 'external' | 'poll';
  revisions?: {                           // current revision per store
    sessions?: number;
    folders?: number;
    appState?: number;
    briefs?: number;
    groups?: number;
  };
  snapshots?: {                           // optional: updated data to avoid round-trip
    sessions?: SessionSnapshot;
    folders?: FolderStore;
    appState?: AppStateSnapshot;
    briefs?: BriefSnapshot;
    groups?: GroupSnapshot;
  };
}
```

#### Runtime change event:

```typescript
window.terminalApi.onRuntimeChanged(callback: (event: RuntimeChangedEvent) => void)

interface RuntimeChangedEvent {
  changed: Array<'terminalState' | 'runtimeState' | 'statusline'>;
  sessionId?: string;                     // which session, if applicable
  data?: {
    terminalState?: TerminalStateSnapshot;
    runtimeState?: RuntimeStateSnapshot;
    statusline?: StatuslineSnapshot;
  };
}
```

#### Renderer refresh rules:

1. **Command snapshots apply immediately.** When a command result includes snapshots, update stores directly — no need to wait for a change event.
2. **Change events refresh only affected slices.** The `changed` array tells the renderer which stores to refresh.
3. **Ignore stale revisions.** If event revision ≤ store's current revision, skip. Prevents double-refresh when command result and change event both arrive.
4. **Debounce/coalesce external events.** Multiple rapid signal file touches → one refresh.
5. **Runtime events never trigger store refresh.** Statusline/terminal/runtime state updates are separate from persisted data.

#### Signal file content:

The `sessions.changed` signal file should include enough information to target refreshes:

```json
{
  "seq": 42,
  "changed": ["sessions", "briefs"],
  "source": "condense.py",
  "timestamp": "2026-04-19T04:00:00Z"
}
```

If the signal file only contains a touch/mtime (legacy), the app refreshes all SQLite-backed slices as fallback.

#### Multi-store command consistency:

Commands that touch multiple stores write in a defined order and emit one combined change event:

Example — `briefs.create`:
1. Write YAML content file
2. Hash YAML content
3. Insert SQLite brief metadata + relationships
4. Add brief card to `all_briefs` root in `folders.json`
5. Emit `changed: ['briefs', 'folders']`

If a crash occurs between steps 3 and 4, startup reconciliation adds missing brief cards to root or marks as unfiled. The app runs reconciliation checks on bootstrap.

### 5.4 External UI Command/Query IPC

A bidirectional channel for external tools to interact with the app's live UI. This is NOT the canonical data API — external tools that need durable session/brief/group/tag data should use `session_store.py` directly. UI IPC is for controlling/querying the live UCI interface.

#### Transport

Main process acts as broker between external tools and the renderer:

```
External tool
  → Unix domain socket (~/Library/Application Support/UnifiedCLI/uci.sock)
  → Electron main process
  → If query needs renderer state: main sends request to renderer with correlation ID
  → Renderer responds
  → Main returns response to external tool
```

Initial implementation assumes one UCI window. If multiple windows exist, UI IPC targets the focused window unless specified.

MCP tools wrap the socket later.

**Requirements:**
- Request IDs for correlation
- 2-second default timeout (configurable)
- If renderer is busy/unavailable: return `UI_UNAVAILABLE` or `TIMEOUT` error
- Same-user restriction (socket permissions)

#### Main ↔ Renderer bridge:

```typescript
// Main → Renderer request
mainToRendererRequest({ requestId: string; type: string; payload?: unknown })

// Renderer → Main response
rendererToMainResponse({ requestId: string; ok: boolean; data?: unknown; error?: unknown })
```

#### Queries

```
ui.query.activeView()                → { activeTabId, mode: 'terminal' | 'folderBrowser', folderBrowserLocation? }
ui.query.activeTab()                 → active tab session ID or null
ui.query.openTabs()                  → ordered list of open tab session IDs
ui.query.folderBrowserLocation()     → FolderBrowserLocation | null (null = folder browser not showing)
ui.query.visibleCards()              → { visible: boolean, cards: CardId[] } (visible=false if folder browser not active)
ui.query.cardDetail(cardId)          → rendered card detail fields (UI presentation, not canonical data)
ui.query.sessionDetail(sessionId)    → rendered session detail fields (UI presentation, not canonical data)
ui.query.selection()                 → currently focused/selected card, if any
ui.query.appSnapshotSummary()        → summary of current app state (tab count, folder count, etc.)
```

Note: `sessionDetail` and `cardDetail` return fields as currently rendered in UCI, not authoritative domain data. For canonical data, use `session_store.py`.

#### Commands

```
ui.command.openTab(sessionId)                    → opens session in a new tab, switches to it
ui.command.focusTab(sessionId, opts?)             → switches to existing tab. opts.showTerminal: true dismisses folder browser.
ui.command.closeTab(sessionId)                    → closes tab
ui.command.showTerminal(sessionId?)               → dismisses folder browser, shows terminal for session (or active tab if no sessionId)
ui.command.dismissFolderBrowser()                 → returns to terminal view of active tab
ui.command.navigateFolderBrowser(location)        → opens folder browser at specified FolderBrowserLocation
ui.command.navigateToFolder(folderId)             → shorthand for navigateFolderBrowser({ kind: 'folder', ... })
ui.command.navigateToView(view)                   → shorthand for navigateFolderBrowser({ kind: 'filterView', ... })
ui.command.navigateToCard(cardId)                 → shorthand for navigateFolderBrowser({ kind: 'cardDetail', ... })
ui.command.showNotification(notification)         → shows structured notification
ui.command.refresh(slices?)                       → forces store refresh (all slices if none specified)
```

Notification structure:
```typescript
interface UciNotification {
  level: 'info' | 'success' | 'warning' | 'error';
  message: string;
  title?: string;
  timeoutMs?: number;
  action?: { label: string; command: string };
}
```

Domain commands (folders.moveCard, tags.add, etc.) are also accessible through the same external socket via:
```
uci.command.dispatch(command)
```
But `uci.command.*` is kept separate from `ui.command.*` — one mutates data, the other controls presentation.

#### Use cases

- A CLI session tells the app to open its tab: `ui.command.openTab("20260413_200951_d2e3b973_cla")`
- An MCP tool queries what the user is looking at: `ui.query.activeView()`
- A script opens a folder after bulk-organizing sessions: `ui.command.navigateToFolder("uci_app")`
- A Condenser session signals completion: `ui.command.showNotification({ level: 'success', message: 'Brief created: Pixel v2' })`
- An external tool checks if the folder browser is active: `ui.query.folderBrowserLocation()` → returns location or null

## 6. Status Model

### 6.1 Three Independent State Axes

UCI tracks three independent concepts:

1. **Terminal/substrate state** — connected, disconnected, killed. Derived from substrate, not persisted. On startup, everything is "unknown" until the substrate reports.

2. **Interaction/runtime state** — running, idle, stopped. Observed from terminal output, not persisted. A terminal can be connected but the session stopped (user Ctrl+C'd). A terminal can be disconnected but the session running (background work).

3. **Archival state** — active or archived. User intent, persisted in SQLite. Carries domain weight — exit interviews, data extraction, saved memories may accompany archival.

### 6.2 Session Kind is Derived

A session's kind (chat vs worker) is derived from its role:
- Has assistant/chat role → chat
- Any other role → worker
- Missing/unknown role on legacy sessions → unknown

Not persisted. Not tracked separately.

## 7. Navigation Model

### 7.1 Two Navigation Systems

The app has two separate navigation systems:

1. **Tab switching** — which session's terminal is shown. Back/Forward navigates through tab viewing history.
2. **Folder browsing** — navigating the folder tree in the center pane. The folder browser is a mode that overlays the tab view.

These are independent. The active tab stays highlighted while the folder browser is showing. Clicking the active tab dismisses the folder browser and returns to the terminal view.

### 7.2 Tab History (Back/Forward)

Back and Forward navigate through tab viewing history — which tabs you looked at, in order.

```
View Tab A → View Tab B → View Tab C → Back → Tab B → Back → Tab A → Forward → Tab B
```

Stored in `app_state.json` as `tabs.viewHistory`:

```json
{
  "backStack": ["session_id_1", "session_id_2"],
  "forwardStack": ["session_id_3"]
}
```

Switching to a tab pushes the previous tab to `backStack` and clears `forwardStack`. Back pops `backStack` and pushes current to `forwardStack`.

First tab on startup has no back target (back disabled).

### 7.3 Folder Browser Navigation

The folder browser shows in the center pane when navigating folders. It has its own internal navigation:

- **Up arrow** — go to parent folder (disabled at root). In card detail: go to card's containing folder.
- **Clicking a subfolder** — navigate into it.
- **Clicking a breadcrumb segment** — jump to that folder.

Folder browser location is renderer state (not persisted). Entering the folder browser does NOT push to tab history. Leaving the folder browser (by clicking a tab) returns to the terminal view.

### 7.4 Folder Browser Location

```typescript
type FolderBrowserLocation =
  | { kind: 'folder'; root: 'sessions' | 'briefs'; folderId: string }
  | { kind: 'filterView'; root: 'sessions'; view: 'claude' | 'codex' | 'gemini' | 'archive' | 'condensers' }
  | { kind: 'cardDetail'; cardId: CardId };
```

### 7.5 Breadcrumbs

Shows path from root to current folder browser location. Each segment clickable.

- **Folder:** `/ > projects > uci_app`
- **Card detail:** `/ > projects > uci_app > Pixel`
- **Filter view:** `All Sessions > View: Claude`

### 7.6 Up Arrow Behavior

| Current Location | Up Target |
|---|---|
| Folder | Parent folder (disabled at root) |
| Card detail | Card's containing folder |
| Filter view | Root (All Sessions) |

## 8. Action Dispatch

### 8.1 Pattern

All user actions flow through a consistent command pattern:

```
Renderer UI event
  → dispatch typed command
  → main process validates + mutates SSOT
  → main process returns result with changed slices + snapshots
  → renderer updates affected stores from result
```

The renderer never directly writes to SQLite, folders.json, or app_state.json.

### 8.2 Command Categories

```
folders.create(parentId, name, icon)
folders.rename(folderId, name)
folders.delete(folderId, policy)
folders.moveFolder(folderId, targetParentId, index?)
folders.reorderSubfolders(parentId, orderedIds)
folders.moveCard(cardId, targetFolderId, index?)
folders.unfileCard(cardId)              // move to root
folders.reorderCards(folderId, orderedCardIds)
folders.getSnapshot()
folders.validateTree()

tags.add(cardId, tag)
tags.remove(cardId, tag)
tags.toggle(cardId, tag)

sessions.archive(sessionId)
sessions.unarchive(sessionId)
sessions.updateDisplayName(sessionId, name)

briefs.create(sourceSessionIds, opts)
briefs.launch(briefName, opts)
briefs.load(sessionId, briefName)
briefs.archive(briefName)

appState.setPinned(sessionId, pinned)
appState.setFolderPref(folderId, key, value)
appState.setPromptBoxConfig(sessionId, config)

uci.getSnapshot()                       // bootstrap: returns all store slices
```

### 8.3 Result Shape

All commands return a consistent result:

```typescript
interface CommandResult<T = unknown> {
  ok: boolean;
  data?: T;
  error?: {
    code: string;
    message: string;
    details?: unknown;
  };
  changed?: {
    sessions?: boolean;
    folders?: boolean;
    appState?: boolean;
    briefs?: boolean;
    groups?: boolean;
  };
  snapshots?: {
    sessions?: SessionSnapshot;
    folders?: FolderStore;
    appState?: AppStateSnapshot;
    briefs?: BriefSnapshot;
    groups?: GroupSnapshot;
  };
}
```

Commands return `changed` flags so the renderer knows which stores to refresh, and optionally `snapshots` with the updated data so stores can update without a second round-trip.

## 9. Renderer State Architecture

### 9.1 Shared Stores

The renderer uses shared stores/hooks — not prop-drilling for domain state.

```
useCardStore()       — union of session cards and brief cards, tags, display fields
useSessionStore()    — session-specific metadata and runtime info
useBriefStore()      — brief-specific metadata (or folded into CardStore)
useFolderStore()     — folder tree snapshot from folders.json
useNavigationStore() — tab history, folder browser location
useAppStateStore()   — UI preferences from app_state.json
useUciActions()      — typed command dispatch
```

All components consume the same stores. NavigationPanel, CardListView, TabBar, FocusPane — all derive their data from shared selectors, not independent IPC calls.

### 9.2 Bootstrap

On app start, renderer requests one bootstrap snapshot:

```typescript
const snapshot = await uci.getSnapshot();
// Initialize all stores from snapshot
```

This ensures all stores start from the same consistent state.

### 9.3 Derived Selectors

Computed from store state, shared across components:

```
visibleCards(location, folderStore, cardStore, appState)
folderPath(folderId, folderStore)
cardLocation(cardId, folderStore)
parentFolder(folderId, folderStore)
descendantCards(folderId, folderStore)
breadcrumbSegments(location, folderStore)
canGoBack(navStore)
canGoUp(location, folderStore)
isCondenser(cardId, cardStore)
```

One function answers "what does the user see?" — not each component computing its own version.

## 10. Menu Architecture

### 10.1 Current Problem

SubMenuItem flyout panels are portals to `document.body`. The parent Popover's capture-phase outside-click handler on `window` sees clicks inside SubMenuItem portals as "outside" and closes the menu before action handlers fire.

Current tactical fix: Popover checks `target.closest('.submenu-panel')`.

### 10.2 Recommended Architecture

Use a menu-layer manager. Each menu layer (root Popover, SubMenuItem panels) registers itself.

```typescript
registerMenuLayer(layerId, element)
unregisterMenuLayer(layerId)

function isInsideAnyMenuLayer(event: PointerEvent): boolean {
  return event.composedPath().some(node => activeMenuLayers.has(node));
}
```

Use `data-menu-root` and `data-menu-layer` attributes instead of class selectors. `event.composedPath()` handles portals correctly.

### 10.3 Menu Dismissal Rules

- Click inside any active menu layer → do not close parent
- Click actionable item → execute action, close entire menu stack
- Click outside all layers → close entire stack
- Escape → close topmost layer first, then parent
- Mouse leave → maybe close submenu after delay, never close root immediately

## 12. Behavioral Specifications

### 12.1 Condenser Filter Behavior

Condensers is a filter checkbox in the filter bar — NOT a View, NOT a folder, NOT a navigation location.

- **Filter off (default):** Condensers are shown alongside all other sessions. They are never hidden.
- **Filter on:** CardListView shows ONLY sessions tagged `condenser`, regardless of which folder is selected.
- There is no "don't show condensers" option. Condensers are always visible.

### 12.2 Store Updates and UI Reactivity

When a command modifies session data (e.g., `tags.add` for "Set as a Condenser"):

1. Command returns `CommandResult` with updated snapshot
2. Shared store (`useCardStore()`) updates from snapshot
3. All subscribed components re-render:
   - **Right Panel Details tab** — receives session from store, re-renders with new tag
   - **Session Details popup (WorkerDetailPopup)** — receives session from store, re-renders with new tag
   - **Context menu labels** — re-render on next open (e.g., "Remove as a Condenser")
   - **Filter results** — if Condenser filter is active, session appears/disappears

Both Session Detail views (Right Panel and popup) use the shared `SessionDetailFields` component. Both receive their session from the same store. Both update in real-time when the store changes.

### 12.3 "Create Brief and Launch" — Menu Label and Stages

Context menu label: **Create Brief and Launch** (not "Compact & Launch").

Placeholder tab stages, in order:

| Stage | Label | When |
|---|---|---|
| 1 | "Finding Condenser..." | Querying SQLite for tagged condensers + checking runtime status |
| 2 | "Compacting..." | Stage 1: stripping tool calls from JSONL |
| 3 | "Condensing..." | Stage 2: Condenser AI producing Brief |
| 4 | "Launching..." | Stage 3: new session starting from Brief |

Error states shown in placeholder tab:

| Error | When |
|---|---|
| "Error: No Condenser available" | No sessions tagged `condenser`, or none are running |
| "Error: Compaction failed" | `compact_jsonl.py` returned error |
| "Error: Condensation failed" | Condenser session errored or timed out |
| "Error: Launch failed" | `launch_from_brief.py` returned error |

Stage progress is emitted via `onRuntimeChanged` channel so the placeholder tab can update visually without touching stores.

The main process owns the entire pipeline. The renderer dispatches one command and receives stage updates + final result. The renderer does NOT orchestrate the steps.

### 12.4 "Set as a Condenser" — Full Flow

1. User right-clicks session tab → Briefings → Set as a Condenser
2. Renderer dispatches: `{ type: 'tags.add', payload: { cardId: 'session:...', tag: 'condenser' } }`
3. Main process: inserts `card_tags` row in SQLite, touches signal file
4. Returns: `CommandResult { ok: true, changed: ['sessions'], snapshots: { sessions } }`
5. Renderer: `useCardStore()` updates. Tag appears in Session Details. Menu label changes to "Remove as a Condenser".

No folders.json change. No app_state.json change. Just one SQLite row.

## 13. What This Design Does NOT Cover

- **Specific UI layouts** — this is data architecture, not visual design
- **Keyboard shortcuts** — separate concern
- **Real-time collaboration** — single-user app
- **Offline/sync** — local-only data
- **Performance optimization** — premature until architecture is stable, but derived metrics may be cached (caches are non-authoritative, invalidated by source mtime/hash)
