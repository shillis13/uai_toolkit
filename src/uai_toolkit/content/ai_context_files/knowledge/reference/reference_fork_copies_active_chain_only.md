Claude Code's session FORK (`--fork-session`, via `fork_session.py --from <id>`) copies **only the active chain** into the new session's transcript — i.e., from the **last compaction summary forward** — NOT the whole `.jsonl` file. The pre-compaction history is **dropped** from the fork (left in the parent's file, which fork leaves untouched).

**Verified empirically 2026-06-29** on Relay (cli d9dc9a30, freshly /self-compacted): parent transcript **90.6 MB** → fork transcript **134 KB / 50 records** = 1 `isCompactSummary` record (the compaction summary) + the post-compaction turns + the test turn. 90.6MB → 134KB is unambiguous: active-chain-only.

(Method: `fork_session.py --from <parent> --oneshot --prompt "<no-op>"` — oneshot headless clone runs one controlled turn and exits; safe, parent untouched. The fork landed in the project dir `-Users-shawnhillis-Documents-AI-ai-root`. CORRECTION (2026-06-30, re-verified): two separate facts were conflated. (1) The FILESYSTEM working dir `~/Documents/AI` is GONE (renamed to `~/Documents/AI.tmp`/`AI.tmp2` ~Jun 14); sessions launched under the old `~/Documents/AI/ai_root` cwd show that stale path in early transcript `cwd` fields. (2) BUT the CLAUDE PROJECT DIR `~/.claude/projects/-Users-shawnhillis-AI-ai-root` **IS a symlink → `-Users-shawnhillis-Documents-AI-ai-root`** (created May 20; `-Documents-…` is the canonical physical storage). So transcripts/archives are NOT hardlinked across two dirs and it's NOT a "ghost via dead-inode writes" — it's ONE physical dir with two names, which is why the same transcript/archive shows identical inodes under both names (verified on Meri's `6b292e23.archive`: dir inode 298254092, manifest 298254353 identical via both paths). Practical upshot: offload/engram archives resolve correctly regardless of which project-dir name a session's cwd maps to. The [[reference_mcp_config_topology]] "Documents/AI symlink" note referred to the FILESYSTEM `~/Documents/AI` (that one is stale/gone); the .claude PROJECT-DIR symlink is real and current.)

**Why it matters:** forking IS a clean "fresh start" that sheds pre-compaction bulk — no custom active-chain-fork tool needed (a concern we'd had for shrinking huge transcripts like Relay's ~90MB). To freshen a bloated session: fork it (new ~small transcript = active chain only), retire the old session; the old file's full history stays intact if ever needed. CAVEAT (unverified): the engram archive dir ([[project_self_bounce_proven]] / [[instr_context_reclaim]]) is keyed to the PARENT filename stem, so offload/consolidate **recall** across a fork is a separate thing to verify before relying on it. Docs (code.claude.com/docs sessions) state fork "copies the history into a new session ID, leaving the original unchanged" but do NOT document the compaction detail — this entry IS that detail.
